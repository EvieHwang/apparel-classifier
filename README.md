# Apparel Classifier

A live web demo that takes real, correctly-labeled apparel records, deliberately
corrupts the `articleType` field, then asks an LLM to recover the original value —
and scores every guess against the ground-truth label.

**Live:** https://apparel-classifier.fly.dev

## Why this exists

Vendor product data arrives with classification errors that compound downstream:
a wrong `articleType` corrupts planning curves, distorts assortment reporting, and
drives bad inventory decisions. The standard fix is a slow, expensive master-data
platform. This demo shows that an LLM already encodes apparel taxonomy well enough
for the team that lives with dirty data to build the instrument that cleans it —
and, just as importantly, it models how to *measure and design for* accuracy,
transparency, and trust when the output is probabilistic and the determination is
automated, not merely suggested.

It is a credibility artifact first: a non-technical peer who receives a forwarded
link should understand what they're looking at, and why it matters, within a minute.

### What this is — and isn't

This recovers **which category** a product belongs to (Tshirts, Jeans, Briefs). It
does **not** normalize vocabulary or formatting — "Tshirt" vs "T-Shirt" vs "tee" is a
separate problem, deliberately left out of v1. One honest caveat: the model leans on
the product **name**, which usually contains the answer, so this measures how
reliably it recovers a category the name already hints at — not classification from
scratch. The **Blank** rows are the closest thing to a cold read, and their accuracy
visibly lags the rest.

This is not a master-data platform or a production pipeline. It uses record metadata
only (never product images), runs over a curated subset rather than the full corpus,
and has no human-in-the-loop review queue.

## How it works

Each run is a four-step loop, streamed to the browser one record at a time:

1. **Sample** — draw N random records (`RUN_SIZE = 12`) from the curated subset.
2. **Corrupt** — damage each record's true `articleType`, tagging it one of three ways:
   - `near-swap` — replaced with a sibling type from the *same* `subCategory`
   - `far-swap` — replaced with a type from a *different* `subCategory`
   - `blank` — wiped to the empty string
   Tags are balanced across the run (counts differ by at most 1) and the corruption is
   deterministic given a seeded PRNG. The true type and `subCategory` are never shown
   to the model, so the answer can't leak.
3. **Classify** — the server sends the model the record's other fields (name, gender,
   colour, season, year, usage, and the corrupted/blank label) and asks for the
   original `articleType`, constrained to the run's closed vocabulary, plus a
   confidence (`low`/`medium`/`high`) and a one-line rationale.
4. **Score** — each prediction is checked against the real label by strict exact
   match. The dashboard shows headline accuracy, an accuracy-by-corruption-type
   breakdown, and a cumulative tally that persists across runs and visitors.

A **single-record panel** runs the same classification path on any product name a
visitor types — there's no ✓/✗ or accuracy there, because a user-supplied name has no
ground truth.

## The dataset

`docs/apparel-subset.csv` (~7,485 rows, 25 article types across 4 subCategories) is a
curated cut of the Kaggle *Fashion Product Images* dataset (`docs/styles.csv`, 44,446
rows). It is produced reproducibly by `pnpm curate` (never hand-edited) and can be
regenerated byte-for-byte from the source. The cut keeps `masterCategory == Apparel`,
retains an `articleType` only if it has ≥50 rows, keeps a `subCategory` only if it
holds ≥2 surviving types (so every record has a near-swap sibling), and caps any one
type at 500 rows (so the head doesn't dominate accuracy). Full rationale:
[`docs/apparel-subset-rationale.md`](docs/apparel-subset-rationale.md).

## Tech stack

- **Next.js 15 / React 19 / TypeScript**, styled with **Tailwind CSS v4**.
- **Anthropic SDK** (`claude-opus-4-8`) with structured outputs — the closed
  vocabulary becomes a `zod` enum so the model can only return a known article type.
- **Server-Sent Events** stream run results to the browser progressively.
- **`node:sqlite`** (Node 22+) backs the cumulative tally, persisted on a Fly volume.
- **Vitest** for the test suite.

### Architecture notes

- The Anthropic API key is read in exactly one place (the `/api/run` and `/api/classify`
  server routes); the SDK and key never reach the browser bundle. A test enforces that
  no client component imports the SDK.
- LLM endpoints are guarded by a per-IP rate limiter (~10 requests/hour) plus an
  app-wide ceiling (240/hour), checked *before* any model call.
- The app runs as a single always-on Fly machine by design: the in-process rate-limiter
  counters and the SQLite cumulative store are correct only on one machine, which the
  mounted volume pins the app to.

### Project layout

```
app/                  Next.js app — dashboard page + API routes
  api/run             SSE classification run (the only key reader for runs)
  api/classify        single-record classification
  api/cumulative      cumulative tally read
  api/health          cheap, LLM-free deploy health check
src/                  headless engine: corrupt, classify, score, cumulative store, rate limit
scripts/curate-subset.ts   reproducible dataset curation (`pnpm curate`)
docs/                 curated subset CSV + curation rationale
features/             per-feature artifacts (declaration, spec, tests)
```

## Run locally

Requires **Node 22+** and **pnpm**.

```bash
pnpm install
cp .env.example .env      # then set ANTHROPIC_API_KEY
pnpm dev                  # http://localhost:3000
```

Other commands:

```bash
pnpm test         # run the Vitest suite
pnpm build        # production build (also the type/compile gate)
pnpm curate       # regenerate docs/apparel-subset.csv from docs/styles.csv
```

### Environment

| Variable | Required | Purpose |
|----------|----------|---------|
| `ANTHROPIC_API_KEY` | yes | Server-side LLM classification calls. |
| `CUMULATIVE_DB_PATH` | no | Path to the cumulative-tally SQLite DB. Defaults to `./data/cumulative.sqlite`; in production it points at the mounted Fly volume. |

See [`.env.example`](.env.example). Never commit a `.env` or any secret values.

## Deployment

Hosted on **Fly.io** (`fly.toml` at the repo root). Pushing to `main` triggers the
GitHub Actions workflow (`.github/workflows/deploy.yml`), which runs `flyctl deploy`
authenticated with a `FLY_API_TOKEN` Actions secret. The release is health-gated: the
HTTP check declared in `fly.toml` against `/api/health` makes the rolling deploy fail
if the new machine never serves, and a post-deploy probe confirms the live app returns
healthy. `ANTHROPIC_API_KEY` is set out-of-band via `fly secrets`, never in `fly.toml`.

CI (`.github/workflows/ci.yml`) runs `pnpm test` and `pnpm build` on every PR and push
to `main`.
